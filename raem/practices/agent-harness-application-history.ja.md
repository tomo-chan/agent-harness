## 3. 仕様、具体化、保証を分離する

### 3.1 実装を仕様の正本にしない

Go実装を先に唯一の基準とすると、CLI、終了コード、パッケージ構造、利用可能なAPI等の偶然の選択が共通契約へ昇格する。PR #16で実装非依存仕様を分離した結果、S1〜S6は同じ契約を参照しつつ、各具体化の部分適合、前提、未決事項を区別できた。

一般化した知識は次のとおりである。

> 仕様は実装の説明書ではなく、複数の具体化と保証が共有する比較基準である。実装で見つけた不足は、実装の挙動を暗黙に仕様化せず、仕様不足、実装エラー、新要求、外部保証責任のいずれかへ分類する。

### 3.2 保証スライスはパッケージでも工程でもない

S1〜S6は順に具体化されたが、各スライスは単一パッケージへ閉じていない。例えばS3はS2のfresh authorityを再利用し、S4はS3の非許可を拡張せず、S6はS1〜S5をベンダーイベントへ接続する。実装部品は共有されても、各スライスの主張、権威、失敗形態、収束条件は分離された。

したがって、順番に実装された事実から、保証スライスを実行フェーズやレイヤー番号と解釈してはならない。

> 保証スライスの境界は、コードの所有場所ではなく、どの主張がどの権威、責任境界、失敗理由、根拠によって成立するかで決める。

### 3.3 部分適合と対象外は収束の失敗ではない

S1〜S6の各変更はAgent Harness全体の完全性を主張せず、対象内の保証規則、決定的テスト、取得不能時の意味論、外部責任、対象外を記録し、歴史上は初回収束点を宣言した。

ただし、後続のPR #5レビューで、独立した信頼済みtask-intent権威の欠落がS5の現在保証を破るモデル指摘と分類された。このため、S5の初回収束宣言は現在有効な収束結果として扱わない。S6のvendor mappingに関する局所的な評価は残るが、S5の完了保証へ依存する部分はtask-intent解決を前提とする条件付き評価である。

対象外を明記することは問題の先送りではない。現在の中心主張と矛盾せず、追跡可能なEvolution入力として残せる場合に限り、保証範囲を固定して収束できる。

## 4. 権威と根拠について得た知識

### 4.1 根拠は主張へ束縛する

S2以降では、リポジトリ識別子、ブランチ、HEAD、既定ブランチ、公開先、ベースコミット、取得時刻を判断Evidenceへ結合した。PR #5の再レビューでは、正しい権威から得た情報でも、別の対象、古い観測、失効後の状態であれば保証を成立させないことを保証契約へ追加した。

> 根拠の適切性は情報源の権威性だけでは決まらない。保証対象、取得時点、有効条件へ結びつき、評価時点で必要な鮮度を持つ必要がある。

### 4.2 権威取得元の選択も信頼された設定である

PR #20では、GitHub Rules APIが対象リポジトリで継続的にHTTP 403となることが判明した。実行時に別APIへ暗黙にフォールバックせず、利用するauthority sourceを信頼された設定で明示し、そのsourceで証明できない詳細要件は要求しない構成へ変更した。

ここから次を得た。

- 複数の情報源が似た値を返しても、同じ保証能力を持つとは限らない。
- 権威取得不能を別の弱い情報源で埋めると、保証主張が暗黙に変わる。
- 利用可能な弱い根拠へ自動退避するより、主張を狭めるか不明として停止する。

### 4.3 暗黙設定は操作意味論の一部である

`branch.<name>.gh-merge-base`、`push.followTags`、Git include、push URL、環境変数、TLS trust selector等は、表面上のコマンドを変えずに実効対象や信頼基点を変え得ることが分かった。

> 操作の正規化は表示されたコマンド文字列だけでなく、実効対象を変える設定、環境、引数境界、暗黙既定値を含めなければならない。

完全な意味解析ができない操作を広く許可するのではなく、自律経路を検証可能な正規形へ限定し、それ以外を承認または拒否へ送る方が保証可能性を高める。

### 4.4 判断Evidenceは永続監査の代替ではない

S2〜S4は判断と根拠を相関できるEvidenceを返すが、保存、完全性、秘匿化、配信、閲覧権限、書込失敗時の停止まで保証しない。構造化された判断出力が存在することと、監査証跡が成立することを同一視してはならない。

## 5. 保証パイプラインについて得た知識

### 5.1 下流の評価は上流の非許可を拡張しない

`deny > ask > allow`の優先、S3非許可時のS4非実行、ベンダーが`ask`を表現できない場合のdeny/blockへの縮小は、すべて同じ原則を表す。

> 保証パイプラインの下流は追加条件によって権限を狭めることはできるが、上流の拒否、不明、承認要求を許可へ広げてはならない。

この単調性を型付きの接続と回帰テストへ固定することで、保証スライス間の組合せを説明しやすくなった。

### 5.2 宣言ではなく実対象と外部作用を評価する

read-onlyを自己申告する未知ツール、表面上安全な複合shell、ローカルoriginだけのリポジトリ同一性、作業ツリーだけの差分検査は、実対象または外部作用との結合が不足する。

S2はmutation target、S3はrefspec・push URL・GitHub branch head、S4はauthoritative baseからの実publication diffへ判断を結合した。

> ツール名や利用者の宣言ではなく、可能な限り実際の対象、差分、宛先、権威ある外部状態に対して保証する。

### 5.3 発見は否定ケースへ移す

compound command、unknown tool、`gh-merge-base`、implicit tag publication、platform path差、CI再帰起動抑止等は、レビュー時の説明だけで閉じず、回帰テストまたはworkflow検査へ移された。

これにより、同じ具体的問題を次回レビューで再発見する必要を減らせる。ただし、否定ケース数の増加だけを成熟とみなさず、複数のケースを説明する上位の保証規則も同時に残す。

## 6. 完了と自律ループについて得た知識

### 6.1 決定的完了条件と意味上の完了を分ける

S5では、リポジトリ状態、GitHub状態、決定的ゲートの成功を、タスク要求の意味上の完了と区別した。決定的検査の初回成功はレビュー要求であり、後続確認でもfreshな決定的保証を再実行する。

> 決定的ゲートは既知の完了条件を保証できるが、タスク要求が意味的に満たされたことを単独では保証しない。反対に、エージェントの完了宣言は決定的条件を上書きしない。

### 6.2 再確認状態を評価対象の書込み可能状態へ置かない

「レビュー済み」等の状態を対象リポジトリへ保存すると、評価対象自身が完了経路を変更できる。S5/S6ではベンダー実行環境が供給するライフサイクル状態を保持して渡し、停止時に権威ある状態を再取得する。

### 6.3 進化ループにも外部上限が必要である

収束条件を定義しても、新しい阻害モデル指摘が毎回見つかれば、レビュー基準の更新と再評価は続き得る。PR #5の再レビューから、回数、時間、ツール呼出し、コスト、連続失敗等をモデルコンテキスト外の制御プレーンが保持し、枯渇時を未完了の `BUDGET_EXHAUSTED` とする知識を追加した。

## 7. 具体実装と配備について得た知識

### 7.1 旧実装ではなく一般化済み知識を継承する

Go化によってPythonのインタープリター、import、複数source、subprocess探索に由来する失敗形態を除去できた一方、ビルド来歴、OS / architecture、署名、更新、失効等の新しい責任が生じた。

PR #30では、旧Python実装との出力一致を適合条件にせず、そこから得た一般化可能な発見だけを保証契約、Goテスト、Evidence、判断履歴へ残した。

> 実装を置き換えるときは、旧構造を保存することではなく、旧構造から得た知識が現行の主張と保証へ移送されたことを確認する。

### 7.2 ベンダー対応は確認済み契約の範囲で主張する

Claude CodeとCodexは公開仕様から停止時の後続確認状態を確認できたが、Devinは同等の公開契約を確認できなかった。そのためcompatibility mappingが存在しても、Devinの本番適合は収束主張から外した。

実装が存在すること、テスト用mappingが存在すること、実製品との適合が立証されていることを区別する。

### 7.3 配布候補の同一性は配備保証の一部にすぎない

build identity、Linux/macOSの独立CI、配布候補、SHA-256 manifestは観測可能な根拠を増やす。しかし、署名、provenance、rollout、rollback、revocation、installed artifact verification、credential containmentは別の外部強制境界を必要とする。

### 7.4 実行環境の意味論も具体化の一部である

macOSの`/var`と`/private/var`、GitHub Actionsの`GITHUB_TOKEN`による再帰workflow抑止、checkoutを持たないjobでのrepository解決失敗は、コード外の環境意味論が保証を破り得る例となった。

これらに対して、信頼境界を弱めてテストへ合わせるのではなく、canonical pathで比較し、freshなPR headを照合して明示dispatchし、repositoryを明示する修正を行った。

## 8. モデル指摘の処理について得た知識

履歴上の発見は、少なくとも次のように分類できる。

| 発見 | 分類 | 処理 |
|---|---|---|
| `gh-merge-base`や`push.followTags`による暗黙対象変更 | 具体化 / 実装エラー | 実効設定を検査し、否定テストへ固定 |
| Rules APIの恒常的403 | 仕様化前提の不足 | authority sourceと証明可能範囲を明示し、暗黙fallbackを禁止 |
| 決定的状態だけではtask intentを判定不能 | 現在保証を破るモデル指摘 | 決定的条件と意味上の完了を分離した上で、独立した信頼済みtask-intent権威を未解決のEvolution入力として残す |
| Devinの公開契約を確認不能 | 外部保証責任 / 適合条件不足 | 本番適合主張を狭め、追加E2Eを条件化 |
| 署名、失効、installed artifact verification | 外部保証責任 | 配備時の追加適合条件として記録 |
| release PRでCIが自動起動しない | 実装エラー | head SHAを照合した明示dispatchを回帰防止として追加 |
| レビュー・進化が無期限に反復し得る | プラクティスのモデル不足 | 外部予算と枯渇状態を追加 |

ここから、モデル影響とサイクル阻害を分ける必要性を確認できた。モデル指摘であっても現在の保証を無効にせず、対象外として正確に説明できるものは次サイクルへ送れる。一方、現在の保証を偽って成立させる欠落は、その重大度ラベルにかかわらず現在サイクルで扱う。

## 9. 実践プラクティスの回顧的評価

### 9.1 履歴から確認できた成果

- 履歴上の具体的な指摘を、適合問題、モデル問題、外部責任へ回顧的に分類できた。
- S1〜S6について、主張から具体化、テスト、Evidence、対象外までの保証ストーリーを回顧的に分離できた。
- 共通実装を複数スライスから利用しながら、下流が上流判断を弱化しない依存関係を記述できた。
- 非決定的レビューの発見を保証規則、回帰テスト、CI、配備条件へ移送できた。

### 9.2 部分的にしか確認できないこと

- S4〜S6には独立した保証スライス文書があり、S1〜S3には実装ノートとPR記録があるが、すべてが本プラクティスの共通形式で記録されているわけではない。
- 識別可能なレビュー基準、観点ごとの完了状態、重大度とモデル影響の分類をS1〜S6で一貫して記録した成果物はない。このため、収束型レビューの全手順を当時実施したとは確認できず、本記録は回顧的・部分的な適用に留まる。
- S1〜S6は歴史上それぞれ初回収束を宣言したが、S5の宣言は後続のtask-intent指摘によって無効化された。S6のS5依存部分も条件付きである。
- 同じ根を持つ指摘の再発見頻度が低下したかは、比較可能な長期測定がない。
- スタックしたPRは依存関係を明示できたが、変更管理コストとの最適な釣り合いは確立していない。
- 保証スライス境界が長期的に安定するかは、今後のEvolutionで再評価が必要である。

### 9.3 確認できていないこと

- Agent Harness以外の対象領域で同じプラクティスが有効か。
- 実配備を含むAgent Harness全体の適合。
- 外部認可、監査永続化、artifact signing / provenance、rollout / rollback / revocation等の外部保証。
- この適用結果だけを根拠に、保証スライス等をRAEM本体へ昇格できるか。

## 10. 次のEvolution入力

この履歴から、次を今後の評価対象として残す。

1. 異なる対象領域へ同じレビュー基準と保証スライス境界判断を適用する。
2. 指摘の再発見率、レビュー観点の完了率、再評価範囲、収束までの予算を観測する。
3. Evidenceと永続監査の契約を接続する。
4. task intentを対象リポジトリやモデルの自己申告から独立して束縛する契約と権威を具体化する。
5. 実配備のartifact / credential / authorization境界を追加保証スライスとして評価する。
6. スタックした変更の依存基線、再評価範囲、マージ順序を機械的に追跡する。
7. 実践プラクティスからRAEM本体へ昇格する候補を、Agent Harness以外の根拠を含む別のモデルレビューで判定する。

## 11. 要約

9月7日以降の履歴は、収束型レビューと保証スライスの概念を使ってAgent Harnessの発見と保証構造を回顧的に整理できることを示した。一方、定義した全レビュープロセスを当時一貫して実施したことや、全スライスが現在も収束していることは示していない。

> 実装、テスト、Evidenceが増えること自体を成熟とみなさない。発見を主張、権威、保証規則、責任境界へ一般化し、決定的な仕組みへ移し、なお保証できない範囲を明示できたときに知識として蓄積される。

この結果は一対象での適用根拠であり、RAEM一般の妥当性や本番配備全体の適合を証明するものではない。
