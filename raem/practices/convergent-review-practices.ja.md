# RAEM実践プラクティス — 収束型レビュー

## 1. 位置づけ

この文書は、具体化・保証・進化モデル（RAEM）そのものの規範を追加するものではない。Agent Harnessリファレンス実装の設計・実装レビューで実際に発生した問題と、その解決過程から抽出したレビュー実践を記録する。

現時点では、ここで定義する概念をRAEM本体へ直接取り込まない。まずRAEM実践プラクティスとして利用し、異なる適用対象でも有効であることが確認できた知識だけを、将来のモデルレビューによってRAEM本体へ昇格させる。

この分離には二つの目的がある。

1. 一つのセキュリティ指向リファレンス実装へRAEM本体を過適合させない。
2. RAEM自身についても、非決定的なレビューで発見した知識を実践で検証し、安定したものだけを決定的・規範的なモデルへ移すというRAEMの進化原則を適用する。

---

## 2. このプラクティスが生まれた背景

Agent Harnessのレビューでは、重大な指摘を修正した後の再レビューで、同種の重大な指摘が繰り返し発見された。

代表例は次のようなものである。

- セッション開始時の書込み可能なキャッシュを権威的判断に利用していた。
- ローカルの遠隔追跡参照を遠隔状態の独立した根拠として扱っていた。
- ローカルGit設定によって公開操作の意味を変更できる可能性があった。
- コマンドの表面的な正規形だけでは、実効的な外部作用を十分に表現できない場合があった。

これらを個別の実装欠陥として逐次修正すると、次のループになる。

```text
レビュー
  ↓
重大な指摘
  ↓
局所修正
  ↓
再レビュー
  ↓
同じ根を持つ別の重大な指摘
  ↓
局所修正
  ↓
...
```

問題はレビュー回数の不足ではなかった。複数の指摘を説明する上位概念を抽出せず、保証対象となる主張、権威、根拠、責任境界、失敗前提を固定しないまま実装を直接レビューしていたことが原因だった。

この経験から、レビューは「指摘を見つけ続ける活動」ではなく、「現在のモデルで指摘を説明できるかを評価し、適合問題とモデル問題を分離しながら、明示された終了条件へ収束させる活動」として扱う必要があると判断した。

---

## 3. 中核原則

収束型レビューは次の原則に従う。

> 指摘を個別に修正する前に、その指摘が現在のモデルで説明可能かを判断する。

現在のモデルで十分に説明できる場合、それは具体化、具体モデル、保証機構などの適合問題として扱う。

現在のモデルでは適切に分類できない、または既存の前提・権威・責任境界そのものを無効にする場合、それはモデル指摘として進化へ送る。

したがって、レビューの基本的な分岐は次のようになる。

```text
指摘
  ↓
現在のモデルと保証契約で説明できるか
  ├─ はい → 適合指摘
  │           ↓
  │        具体化・具体モデル・保証を修正
  │
  └─ いいえ → モデル指摘
              ↓
           モデル進化
              ↓
           新しいレビュー基準
```

新しい攻撃経路、新しい実装手段、新しい例外を発見したこと自体は、モデル指摘であることを意味しない。既存モデルがその問題を一般的に説明できるなら、それは既存モデルへの不適合である。

---

## 4. 主張を先に固定する

レビューを実装ファイルから開始しない。

最初に、対象が成立させようとしている重要な主張を抽出する。

例えばAgent Harnessでは、次のような主張が存在する。

- 実行対象リポジトリの同一性を信頼済みの情報から確定する。
- リポジトリ保護状態が所定の要求を満たす場合だけ遠隔変更を許可する。
- 直接的な自律公開は定義済みの範囲に限定される。
- 制御機構の変更は公開前に審査される。
- 完了判定はモデル自身の主張ではなく機械的根拠から導出される。
- 認証情報侵害が単独で無制限の外部権限へ拡大しない。

この段階では実装方法を主張へ混ぜない。

「`origin/main` と比較する」は主張ではなく具体化である。「権威的な既定ブランチ状態と現在状態が一致することを確認する」が主張である。

---

## 5. 権威・根拠分析

### 5.1 なぜ必要か

Agent Harnessレビューでは、複数の重大な指摘が「同じ権限領域から変更可能な状態を独立した保証根拠として扱っていた」という一つの問題へ一般化できた。

ただし、「変更可能な情報は信用しない」という二値分類も強すぎる。

ローカルHEADや作業ツリーは評価対象から変更可能だが、現在の対象状態を観測するためには必要である。

そのため、根拠を少なくとも次の役割へ分ける。

### 5.2 観測

評価対象の現在状態について得られる情報。

例:

- 現在のHEAD
- 現在ブランチ
- 作業ツリー
- ローカル設定

観測は対象から変更可能であってもよい。対象の状態を知ること自体が目的だからである。ただし、観測だけで独立した外部事実を保証してはならない。

### 5.3 主張入力

評価対象側から与えられる要求、宣言、設定。

例:

- リポジトリ固有の追加方針
- アーキテクチャ宣言
- メタデータ

主張入力はモデルへの入力には利用できるが、それ自身を上位の権威として扱わない。

### 5.4 権威

対象の主張とは独立して、特定の判断を成立させる権限または情報源。

Agent Harnessでは、例として次の領域がある。

```text
エージェント権限領域
  リポジトリ / .git / ローカルプロセス / 一時状態
          │
          │ 信頼境界
          ▼
ハーネス権限領域
  信頼済み実装 / 信頼済み最低基準
          │
          │ 外部権威境界
          ▼
SCM・組織権限領域
  リポジトリ側規則 / IAM / 組織方針
```

この具体的な領域構造はAgent Harness固有であり、RAEM一般の必須構造とはしない。

一般化できるのは次の原則である。

> 根拠の適切性は、根拠単独では決まらない。どの主張を成立させるために、どの役割と権威性を持つ根拠が必要かによって決まる。

---

## 6. 保証契約

主張をレビュー可能な単位へ落とすため、重要な主張ごとに保証契約を作る。

保証契約は最低限、次を記述する。

| 項目 | 意味 |
|---|---|
| 主張 | 何が成立すると保証するのか |
| 観測 | 評価対象から何を観測するのか |
| 権威 | どの独立した判断源を必要とするのか |
| 根拠対象 | どのリポジトリ、ブランチ、参照、リビジョン、モデル状態等についての根拠か |
| 取得時点 | 根拠をいつ、どの評価時点で取得したか |
| 有効条件 | どの期間・状態・操作まで有効で、何が変化したら再取得するか |
| 前提 | この保証が成立するために仮定するもの |
| 失敗形態 | どのように保証が成立しなくなるか |
| 責任境界 | どの機構・システムがその失敗を扱うか |
| 保証規則 | 根拠からどのように結果を決定するか |
| 対象外 | この契約が保証しないもの |

例:

| 項目 | 例 |
|---|---|
| 主張 | 現在HEADが権威的な既定ブランチ状態と一致する |
| 観測 | ローカルHEAD、作業ツリー |
| 権威 | SCMが返す既定ブランチ状態 |
| 根拠対象 | 検証済みリポジトリ識別子、既定ブランチ参照、評価対象のローカルHEAD |
| 取得時点 | 適合評価の直前にSCMとローカル状態から取得した時点 |
| 有効条件 | 同じリポジトリ・参照・リビジョンに対する評価中だけ有効とし、公開直前または対象状態の変化後に再取得する |
| 前提 | 信頼済み評価器が評価対象から変更不能 |
| 失敗形態 | 外部状態取得不能、対象不一致、観測不能 |
| 責任境界 | ハーネス + SCM |
| 保証規則 | 一致かつ所定状態なら成立、それ以外は不成立または不明 |
| 対象外 | ローカルGit実装自体の完全性 |

保証契約の目的は、すべてを一つの機構で保証することではない。

むしろ、ある失敗がハーネス、サンドボックス、IAM、SCM、組織統治などのどこへ割り当てられているかを明示し、レビューが責任境界を際限なく越えて拡大することを防ぐ。

権威ある情報源から得たという事実だけでは、根拠の適切性は成立しない。根拠は保証対象へ結びつき、評価に必要な鮮度を持たなければならない。別リポジトリ、別ブランチ、別リビジョンに対する応答や、有効条件を過ぎたキャッシュは同じ権威から得たものであっても利用しない。対象、取得時点、有効条件のいずれかを確認できない場合は、保証を成立または完了と判定せず、根拠を再取得するか不明として扱う。

## 7. レビュー基準

モデルは進化可能でなければならない。一方、レビュー中に評価基準を暗黙に変更し続けると適合を判定できない。

そこで、レビューごとに評価対象となるモデル状態をレビュー基準として識別する。

レビュー基準はRAEM全体を凍結しない。今回のレビュー対象となる主張と、その主張が依存するモデル部分だけを識別する。

例:

```text
レビュー基準 RB-001

対象主張:
  C01 リポジトリ同一性
  C02 保護状態
  C03 公開
  C04 完了

依存:
  抽象要求 A-01..A-04
  具体化規則 R-01..R-08
  保証契約 AC-01..AC-04

前提:
  ...

対象外:
  ...
```

レビュー基準はモデル変更を禁止するものではない。

重大なモデル指摘によって基準そのものが不十分と判明した場合、レビューを中断して進化へ戻り、新しい基準を作成する。

```text
RB-001
  ↓
モデル指摘
  ↓
進化
  ↓
モデル更新
  ↓
RB-002
```

適合判定は、どのレビュー基準に対する結果なのかを追跡可能にする。

---

## 8. 指摘分類

指摘には少なくとも二つの独立した軸を持たせる。

### 8.1 重大度

重大度は影響の大きさと緊急性を表す。

例:

- P0
- P1
- P2
- P3

具体的な重大度体系は適用組織が定義してよい。

### 8.2 モデル影響

モデル影響は、どの層を変更する必要があるかを表す。

例:

- なし
- 保証
- 具体化
- 抽象モデル

したがって、`P1 / 具体化` と `P1 / 抽象モデル` は異なる意味を持つ。

前者は重大だが現在の抽象モデルで説明できる。後者は重大であり、現在のモデル自体を再検討する必要がある。

### 8.3 モデル指摘の判定

新しい問題を発見しただけではモデル指摘としない。

次のいずれかに該当する場合にモデル指摘を検討する。

- 現在のモデルや保証契約では適切に分類できない。
- 既存の重要な前提を無効にする。
- 権威・責任境界そのものを変更する。
- 複数の具体化に共通する抽象要求が欠落している。
- 現在の保証規則が、モデル上不適合な状態を適合と判定し得ることがモデル上の欠落に由来する。

逆に、既存モデルが問題を一般的に説明でき、具体実装だけがそれに違反している場合は適合指摘である。

---

## 9. モデル指摘を発見したときの振る舞い

すべてのモデル指摘でレビューを中断する必要はない。

ただし、次のような看過できないモデル指摘は、現在の基準による適合判定を継続せず、進化へ戻す。

- 重要な安全・セキュリティ不変条件を破る可能性がある。
- 主要な主張を成立させない可能性がある。
- 信頼境界または権威境界を変更する。
- 根拠の独立性・適切性を否定する。
- 具体化の前提が誤っている可能性がある。
- 複数の重要な具体機構へ横断的に影響する。
- 現在の保証が重大な偽陽性を返す可能性がある。

処理は次のようにする。

```text
看過できないモデル指摘
  ↓
現在の適合レビューを一時停止
  ↓
モデルレビュー / 進化
  ↓
抽象モデル・具体化・保証契約等を更新
  ↓
新しいレビュー基準を作成
  ↓
影響を受ける主張を再評価
```

これは「モデルが未成熟だからレビューを終えられない」という無限ループを正当化するための仕組みではない。次節のレビュー網羅性と収束条件を併用する。

### 9.1 レビュー・進化サイクルの資源上限

レビュー基準の更新と再評価を繰り返すサイクルには、モデルやレビュー担当エージェントの自己判断とは独立した上限を設ける。

上限はオーケストレーター等の制御プレーンがモデルコンテキスト外で保持・強制し、少なくとも適用対象に応じて次を組み合わせる。

- モデル進化または再レビューの回数
- 経過時間
- ツール呼出し回数
- トークン、計算量、金額等のコスト
- 同一原因による連続失敗回数

各サイクルへ入る前に残予算を検証し、消費を正本へ記録する。モデル指摘、レビュー基準の更新、担当エージェントの変更、再起動、引き継ぎによって予算を暗黙に初期化してはならない。

```text
モデル指摘
  ↓
制御プレーンが残予算を検証
  ├─ 予算あり → 進化 → 新しいレビュー基準 → 影響範囲を再評価
  └─ 予算枯渇 → BUDGET_EXHAUSTED
                    ↓
                  未解決指摘・根拠・残存リスクを保存
                    ↓
                  外部判断（対象縮小 / 追加予算 / 中止）
```

`BUDGET_EXHAUSTED` は収束、適合、完了ではない。現在の保証を無効にする指摘が残る場合はマージ可能へ読み替えず、安全側で停止する。追加予算による再開は、権限を持つ外部主体が対象、上限、再開点を明示した場合だけ行う。

## 10. レビュー網羅性

レビュー回数を収束条件にしない。

「もう一度レビューすれば別の問題が見つかるかもしれない」という理由だけで同じ非決定的レビューを無期限に繰り返さない。

代わりに、対象に応じたレビュー観点を事前に定義する。

Agent Harnessから抽出された代表的な観点は次のとおりである。

| 観点 | 問い |
|---|---|
| 権威 | 最終判断権を誰が持つか |
| 信頼境界 | 評価対象が保証機構やその前提を変更できないか |
| 根拠完全性 | 根拠を誰が生成・変更できるか |
| 失敗形態 | 各依存が失敗したときに何が起こるか |
| 迂回 | 想定した制御経路を通らない場合に重要な不変条件が残るか |
| 責任分担 | どの境界がどの失敗を封じ込めるか |
| 保証欠落 | 重要な主張に対応する保証規則と根拠があるか |
| 適合 | 具体モデルが実際にモデル・保証契約へ従っているか |

これらはRAEM一般の固定チェックリストではない。適用対象に応じて追加・削除する。

各観点について、少なくとも次の状態を記録する。

```text
未レビュー
レビュー済み・問題なし
未解決指摘あり
非該当・理由記録済み
```

これにより「レビューした」という曖昧な状態ではなく、何を探索済みかを明示できる。

---

## 11. 収束条件

収束を「未知の問題が存在しないこと」と定義してはならない。

非決定的レビューによって未知が存在しないことを証明することはできない。

このプラクティスでは、収束を次のように扱う。

```text
収束
  = 安定したレビュー基準
  + 必要なレビュー観点の完了
  + マージを妨げる未解決指摘がない
  + 看過できないモデル矛盾がない
  + 残存リスクと対象外が明示されている
```

より具体的には、次を満たした場合にレビューを収束させる。

1. 対象となる重要な主張が識別されている。
2. 重要な主張について必要な保証契約が存在する。
3. レビュー基準が識別されている。
4. 必要と判断したレビュー観点がすべてレビュー済み、または理由付き非該当である。
5. マージを妨げる適合指摘が残っていない。
6. 現在のレビュー基準を無効にする看過できないモデル指摘が残っていない。
7. 対象外、前提、残存リスクが明示されている。
8. レビュー・進化サイクルの予算が枯渇していない。

P2などの非阻害的なモデル指摘を進化バックログへ送ることはできる。ただし、その判断自体を記録する。

## 12. レビューの標準プロセス

```text
1. 変更目的を確認
      ↓
2. 重要な主張を抽出
      ↓
3. 権威・根拠・責任境界を分析
      ↓
4. 保証契約を定義または確認
      ↓
5. レビュー基準を確立
      ↓
6. 定義済み観点で横断レビュー
      ↓
7. 指摘を重大度 × モデル影響で分類
      ↓
8a. 適合指摘
      → 具体化 / 具体モデル / 保証を修正

8b. 看過できないモデル指摘
      → レビュー停止
      → 制御プレーンが残予算を検証
        ├─ 枯渇 → BUDGET_EXHAUSTEDとして停止
        └─ 残あり
      → 進化
      → 新しいレビュー基準
      → 影響範囲を再評価
      ↓
9. 決定的な適合保証を実行
      ↓
10. レビュー網羅性と残存リスクを確認
      ↓
11. 収束判定
```

修正後に常にレビュー全体を最初から繰り返す必要はない。

適合指摘だけなら、その指摘が影響する保証契約とレビュー観点を再評価する。モデル指摘によって基準が変更された場合は、その変更によって影響を受ける主張を特定して再評価する。

---

## 13. AIエージェントの役割

このプラクティスでは、AIエージェントを単なる指摘生成器として扱わない。

AIエージェントの重要な役割は、指摘を既存モデルとの関係で分類し、複数の具体的指摘から一般化可能な知識を抽出することである。

```text
具体的な複数の指摘
  ↓
共通原因を探索
  ↓
既存モデルで説明可能か
  ├─ はい → 適合知識として具体化・保証へ固定
  └─ いいえ → モデル指摘として進化へ投入
```

Agent Harnessでは、書込み可能なキャッシュ、遠隔追跡参照、ローカルGit設定などの個別問題から、「主張に対してどの権威領域の根拠を利用できるか」というより一般的な問いが抽出された。

成熟したレビューでは、問題の列挙を増やすより、複数の問題を説明できるより少数の原則を探索する。

これはRAEMにおける「非決定的な探索で得た安定した知識を決定的な仕組みへ移す」という役割分担の、レビュー領域への適用である。

---

## 14. RAEM本体との境界

このプラクティスから得られた知識のうち、次の一般原則はRAEM本体との整合性が高い。

- 根拠は、対象となる主張に対して適切でなければならない。
- 適合保証は、具体モデルが抽象モデルへ適合することを評価するのであり、抽象モデル自体の完全性を保証しない。
- モデルレビューでは、現在のモデルで十分説明できない重要な指摘を進化へ送る必要がある。
- 適合評価は、識別可能なモデル状態に対して行われなければならない。

ただし、これらをRAEM本体へ追加するかは、この文書の採用だけでは決定しない。別のモデルレビューで判断する。

次の概念は現時点では実践プラクティスに留める。

- 権威領域の具体的分類
- 保証契約の具体フォーマット
- レビュー基準の識別方法
- P0/P1/P2/P3などの重大度体系
- モデル影響分類
- レビュー網羅性表
- 具体的なレビュー観点
- プルリクエスト上の運用手順

これらは有用であっても、Agent Harnessのようなセキュリティ・権限境界が重要な適用対象へ偏っている可能性がある。

---

## 15. RAEM本体への昇格条件

実践プラクティスの概念をRAEM本体へ昇格させる場合、少なくとも次を確認する。

1. Agent Harness以外の異なる種類の適用対象でも同じ問題を説明できる。
2. その概念を除くとRAEMの一般的な具体化・保証・進化を説明できない、または重大な曖昧性が残る。
3. 特定の製品、セキュリティ機構、SCM、実装方式に依存しない表現へ一般化できる。
4. RAEM本体へ追加しても、実践手順を規範モデルへ過剰に持ち込まない。
5. モデルレビューによって既存概念との重複・矛盾がないことを確認する。

昇格しないことは、そのプラクティスの価値が低いことを意味しない。RAEM本体は小さく一般的に保ち、具体的な適用知識はプラクティスとして発展させること自体が望ましい。

## 16. このプラクティス自身の評価

この文書は、Agent Harnessリファレンス実装のレビューから一度抽出した仮説的な実践モデルである。

したがって、この文書自身も完成した規範として扱わない。

2026年9月7日以降、Agent Harnessの実装非依存仕様、S1〜S6保証スライス、Go-only production line、配布経路へ実際に適用した。観測、一般化した知識、決定的な仕組みへ移した内容、未立証範囲は[Agent Harness適用履歴から得た知識](agent-harness-application-history.ja.md)に記録する。

この適用では次を確認できた。

- Agent Harness PRの指摘を適合問題、モデル問題、外部保証責任へ分類できた。
- 各保証スライスに収束条件、対象外、残存リスクを置き、レビューの終了理由を説明できた。
- review findingを保証規則、否定テスト、CI、配備条件へ移送できた。
- 保証できない製品契約や配備責任を適合主張から外し、責任境界を維持できた。

一方、指摘の再発見頻度が長期的に低下したか、Agent Harness以外でも有効か、RAEM本体へ昇格できるほど一般的かは確認できていない。利用結果から安定した知識が得られた場合も、未立証範囲と分けてこのプラクティス自身を進化させる。

## 17. 要約

このプラクティスの中心は、レビュー回数を増やすことではない。

> 指摘を現在のモデルで説明できるかを判断し、説明できるものは適合問題として閉じ、説明できない重要なものはモデル進化へ送る。

そのために、重要な主張、根拠の役割と権威、保証契約、レビュー基準、指摘分類、レビュー網羅性、残存リスクを明示する。

収束とは未知がなくなることではない。

> 明示されたレビュー基準に対して必要な探索を完了し、重大な未解決適合とモデル矛盾がなく、残存する前提・対象外・リスクを説明できる状態を収束とする。

この方法自体をまずRAEM実践プラクティスとして使用し、その有効性を複数の適用事例から評価した後、十分に一般化された知識だけをRAEM本体の進化候補とする。
