# セキュリティモデル

このセキュリティモデルでは、エージェント、リポジトリ内コード、リポジトリ固有設定が誤っている、または敵対的である可能性を前提とする。大規模言語モデル自体をセキュリティ境界とはみなさない。

重要な不変条件は、信頼済み起動状態、信頼済みハーネス実装、意味論的フック、サンドボックスとワークロードの能力境界、最小権限のIAM / SCM権限、サーバー側リポジトリ規則へ分担する。

## 脅威モデル

自律エージェントは、誤った判断、悪意あるリポジトリ指示への追従、予期しない副作用を持つリポジトリ内コードの実行、認証情報の直接・間接取得、制御機構ファイルの変更、意図しないリポジトリや参照への公開を行う可能性がある。

また、`pytest` など許可済みコマンドが、フックから直接観測できない子プロセスを起動する可能性も前提とする。そのため、モデルの完全な判断、指示への完全な従属、フックによる完全仲介には依存しない。

## 信頼済み権威とリポジトリ入力

信頼済み作業対象識別は `AGENT_HARNESS_EXPECTED_REPOSITORY` が担う。本番の方針評価器、保護状態評価器、意味論検証器は、エージェントが変更可能なワークスペースの外にある `AGENT_HARNESS_TRUSTED_ROOT` から実行する。

リポジトリ保護状態の方針には、権威の異なる二つの入力を使う。まず `AGENT_HARNESS_TRUSTED_REPOSITORY_SECURITY_POLICY` または組み込みの `restricted` 基準から、信頼済み最低基準を得る。さらに、信頼済み起動処理は `AGENT_HARNESS_MINIMUM_POSTURE_MODE` によって最低基準モードを明示できる。これは対話用途で意図的に `warn` を選択する運用を維持するための、信頼済み権威による指定である。

その後、リポジトリ内の `.agent-harness/security.json` を未信頼の強化入力として単調に合成する。

```text
信頼済みモード     = 起動処理の明示指定があればその値、なければ最低基準ファイルの値
有効モード         = より厳しい(信頼済みモード, リポジトリモード)
有効必須要件       = 信頼済み要件 OR リポジトリ要件
有効キャッシュ時間 = min(信頼済み時間, リポジトリ時間)
```

リポジトリ側は制御を追加したり、より厳しいモードを選んだりできるが、信頼済み必須要件を解除したり、信頼済みキャッシュ時間を延長したりできない。リポジトリ側の `expected_repository` は追加の整合性主張であり、信頼済み作業対象識別を置き換えられない。不正な信頼済み方針またはリポジトリ方針は `BLOCKED` とする。

## リポジトリ権威状態

SessionStartでは、リポジトリ識別、GitHubのリポジトリ情報、既定ブランチに適用される有効な規則を評価する。各必須根拠は `pass` / `fail` / `unknown` に正規化する。

有効方針から次の権威状態を導出する。

- `READY` — 必須根拠が有効方針を満たす、または信頼済みの `warn` 指定が不一致を警告として許容する
- `RESTRICTED` — ローカル開発は継続できるが、遠隔SCM変更を拒否する
- `BLOCKED` — 変更操作を拒否する

権威状態は承認より先に評価する。`BLOCKED` はネイティブ承認や信頼済み外部承認でも弱められない。`RESTRICTED` も遠隔SCM変更を承認経路で許可できない。保護状態のキャッシュは、有効期限切れまたはリポジトリルート変更時に再評価する。

## 直接操作に対する意味論的方針

フックが統治するのは、フック境界で観測できるエージェント直接操作である。任意の子プロセスの副作用まで完全仲介するとは主張しない。

直接の自律的Git公開は次の2形式だけに限定する。

```bash
git push
git push --set-upstream origin HEAD
```

検証器は、保護状態が `READY` であること、現在ブランチが名前付きかつ既定ブランチではないこと、`origin` が検査済みリポジトリと一致すること、上流ブランチが期待どおりであることを確認する。

強制pushは `--force-with-lease=<参照>` を含む形式も拒否する。自律的な `gh pr create` はリポジトリ、作業元ブランチ、基準ブランチを上書きできず、現在ブランチが `origin/<現在ブランチ>` として公開済みである必要がある。

複合シェルは自律許可対象外とする。さらに、リポジトリ権威状態の強制では、遠隔SCM変更がコマンド途中に存在しても保守的に検出する。これにより `git status && git push` のような操作で `RESTRICTED` を承認経路から迂回できない。

## 制御機構の公開時審査

ローカルの制御機構ファイルは本番の信頼起点ではないが、それらの変更は公開前に明示審査する必要がある。編集時のパス規則は多層防御とし、編集経路に依存しない主要な保証点は公開差分とする。

正規形pushまたは自律的なプルリクエスト作成の前に、`origin/<既定ブランチ>...HEAD` に対する変更ファイルを評価する。ベンダー用フック設定、`.agent-harness/`、CI、ハーネス、保護状態検査、方針、起動処理、`AGENTS.md` などの保護対象が変更されていれば、明示承認を要求する。差分を確立できない場合は安全側へ倒して拒否する。

この方式は、変更が書込み・編集ツール、`apply_patch`、Gitの復元操作、リポジトリ内スクリプトなど、どの経路で作られたかに依存しない。本番で実行される権威実装は引き続き読み取り専用の信頼済みハーネス領域が担う。

## 認証情報侵害の封じ込め

認証情報を秘匿することは望ましいが、それだけをセキュリティ不変条件にはしない。許可済みリポジトリコードが、直接取得を拒否していても実行時権限を観測または悪用する可能性がある。

そのため、認証情報侵害を起こり得る故障形態として扱い、短寿命・リポジトリ限定・最小権限の認証情報と、GitHub側の権威的な規則によって影響範囲を封じ込める。標準配備は1 Pod / 1エージェントコンテナとし、認証情報を隠すことだけを目的にSCM仲介サービスやサイドカーを追加しない。

## 完了保証

完了はモデルの自己申告ではなく根拠によって判断する。SessionStartでリポジトリルート、`HEAD`、未追跡ファイルを含む正確な作業ツリー状態を保存し、Stopで現在状態と比較する。

- 状態が不変なら、読み取り専用セッションである決定的な根拠として扱い、成果物向けの機能ブランチ・上流ブランチ条件を要求しない
- 状態が変化していれば、通常の決定的な成果物完了検査を実行する
- 基準状態が欠落、不正、または比較不能なら、読み取り専用とはみなさず通常の完了検査を実行する

これにより、レビューや調査だけのセッションを利用可能に保ちつつ、変更を伴う成果物作業は安全側へ倒す。

## 責務分担

各要素の権威を次のように分離する。

- 信頼済み起動処理 — 作業対象識別と信頼済み保護モードの意図
- 信頼済みハーネス領域 — 方針・評価器実装と信頼済み最低基準
- リポジトリ固有方針 — アプリケーション固有の制約追加のみ
- 意味論的フック — 直接観測できる操作の分類とライフサイクル接続
- サンドボックス / コンテナ — ローカル能力低減とワークロード隔離
- IAM / SCM認証情報 — 侵害時の影響範囲制限
- GitHubルールセット / ブランチ保護 — 遠隔リポジトリに対する権威的強制
- 決定的な検査・判定 — 定義済み主張に対する適合根拠
- 人間またはAIエージェントによるモデルレビュー — 既存の保証規則に表現されていない未知の欠落の発見

単一の層を完全なセキュリティ強制機構とは説明しない。

## 失敗時の扱い

セキュリティ上重要な評価エラーは、実行環境が許す範囲で安全側へ倒す。`unknown` は `fail` と区別し、取得不能な外部根拠を暗黙に `pass` へ昇格させない。

任意のリポジトリ固有方針が存在しないことは正常であり、信頼済み最低基準をそのまま使う。明示された方針が不正な場合は制御機構の失敗として扱う。

## 具体化・保証・進化モデル上の位置づけ

この実装では、主張、具体化、根拠、適合保証を分離する。これまでのモデルレビューでは、ワークツリー内検証器の自己変更、フックによる完全仲介の過大主張、`BLOCKED` の承認迂回、SCM状態拘束の不足、リポジトリ方針の上書き、編集時だけの制御機構審査、読み取り専用セッションに対する停止時検査などの欠落を発見した。安定した知識は判断記録と決定的な回帰検査へ移している。

DL-019の最初の実装では、`.github/...` の先頭の `.` を誤って削除するパス正規化欠陥があり、新たに追加した回帰検査がCIで失敗した。マージ前に修正できたことは、モデルレビューによる進化と、決定的な適合保証が別の役割を持つことを具体的に示している。
