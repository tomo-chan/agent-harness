# DL-017 — 権威状態を承認より優先する

- 状態: 採用
- 日付: 2026-09-06

## 背景

リポジトリ安全状態確認は `READY`、`RESTRICTED`、`BLOCKED` を返します。従来の実装では、中央方針が `allow` を返した場合にだけ安全状態を適用していました。そのため、変更操作が `ask` に分類されると、リポジトリ安全状態が `BLOCKED` であっても製品側の承認経路へ到達できる可能性がありました。

これは「`BLOCKED` では変更操作を拒否する」という既存の不変条件と矛盾します。また、本来は環境の適格性を表す権威状態が、個別操作に対する承認判断より弱くなっていました。

## 判断

リポジトリ安全状態は権威状態として扱い、変更操作については通常の `allow` / `ask` 判定より先に評価します。

優先順位は次の通りです。

```text
非変更操作
    -> 通常の方針結果

変更操作
    -> リポジトリ権威状態
        BLOCKED    -> 拒否
        RESTRICTED -> 外部SCM変更を拒否
        READY      -> 続行
    -> 通常の allow / ask / deny
    -> 必要に応じてSCM正規形の意味論検証
```

したがって `BLOCKED` は、製品固有の承認画面、`ask`、通常の方針規則に対する外部承認によって弱められません。変更操作を再開するには、承認を与えるのではなく、リポジトリ安全状態そのものを改善し、再評価する必要があります。

`RESTRICTED` は意図的に範囲を限定します。ローカル開発は継続できますが、外部SCM変更は拒否します。通常の方針規則を承認しても、制限中の外部公開を許可済みに変換することはありません。

## RAEM上の解釈

### 抽象的不変条件

変更禁止を宣言する権威状態は、下位の承認機構によって弱められてはならない。

### 具体化

二種類の判断を分離します。

1. **権威状態の判断** — 現在の環境が、その種類の操作を実行する資格を持つか。
2. **承認判断** — 実行資格がある操作に対して、人間または外部承認が必要か。

まず権威状態による実行資格を評価し、その後に個別操作の承認を評価します。

### 具体モデル

`reference/harness/common.py` では、変更を伴う `PreToolUse` 操作について、通常の `ask` を返す前、または通常の `allow` を適用する前にリポジトリ安全状態を評価します。

### 根拠

回帰検査で次を確認します。

- `BLOCKED` は通常許可される変更操作を拒否する。
- `BLOCKED` は `ask` の変更操作より優先される。
- `BLOCKED` は外部承認によって `allow` に昇格済みの変更操作より優先される。
- `BLOCKED` 中でも読み取り専用操作は継続できる。
- `RESTRICTED` はローカル変更を許可しつつ、外部SCM変更を拒否する。

## 影響

- 製品固有の承認画面から `BLOCKED` を迂回できません。
- 外部承認は安全状態の改善手段ではありません。
- 操作再開には、安全状態が依存する失敗・未確認の根拠を改善し、再評価する必要があります。
- 権威と承認の違いが明示され、人間とAIエージェントの双方がレビュー可能になります。

## 再評価条件

リポジトリ安全状態を、より一般的な能力・権威モデルへ置き換える場合、または将来の実行環境が権威状態の優先関係を構造化して表現できる認可機構を提供した場合に再評価します。
