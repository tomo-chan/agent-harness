# DL-018 — 信頼済み方針とリポジトリ方針を単調に合成する

- 日付: 2026-09-06
- 状態: 採用。方針モデル変更時に再評価
- 対象: リポジトリ保護状態 / 信頼済み起動処理 / リポジトリ固有の安全方針

## 判断

リポジトリの安全状態は、信頼済み権威と未信頼のリポジトリ固有方針を組み合わせて導出する。

信頼済み権威は次の二つから構成する。

1. `AGENT_HARNESS_TRUSTED_REPOSITORY_SECURITY_POLICY` が指す信頼済み最低基準ファイル。未指定時は組み込みの `restricted` 基準を使う。
2. 信頼済み起動処理が必要に応じて指定する `AGENT_HARNESS_MINIMUM_POSTURE_MODE`。対話用途で明示的に `warn` を選択する既存の運用を維持する。

起動処理による指定が変更するのは信頼済み最低基準のモードだけである。必須要件とキャッシュ時間は信頼済み最低基準ファイルから取得する。その信頼済み基準を確定した後で、`.agent-harness/security.json` を未信頼のリポジトリ固有方針として読み込む。

リポジトリ固有方針は信頼済み基準を強化できるが弱化できない。現在の方針語彙では次のように合成する。

```text
信頼済みモード     = 起動処理の指定があればその値、なければ最低基準ファイルの値
有効モード         = max(信頼済みモード, リポジトリモード)
有効必須要件       = 信頼済み要件 OR リポジトリ要件
有効キャッシュ時間 = min(信頼済み時間, リポジトリ時間)
```

リポジトリ側の `expected_repository` は追加の整合性主張として扱う。信頼済みの作業対象リポジトリ識別は引き続き `AGENT_HARNESS_EXPECTED_REPOSITORY` が担い、リポジトリ自身の設定では置き換えられない。

## 具体化・保証・進化モデル上の理由

信頼済みハーネス境界を導入した際、リポジトリ固有方針そのものを信頼済み方針で置き換えていた。その結果、信頼境界は強化された一方で、DL-012で定義した具体化契約と具体モデルが一致しなくなった。

したがって要求は「リポジトリ方針を信頼する」でも「リポジトリ方針を無視する」でもない。

> 信頼済み方針が下限を定め、リポジトリ方針は制約を追加できるが、信頼済み制約を削除できない。

`AGENT_HARNESS_MINIMUM_POSTURE_MODE` はリポジトリ入力ではなく、信頼済み起動処理の権威に属する。そのため、対話用途ではリポジトリ固有方針を合成する前に、信頼済み基準として明示的に `warn` を選択できる。リポジトリ側は、その選択済み基準をさらに弱めることはできない。

## 失敗時の扱い

信頼済み最低基準、信頼済み起動処理が指定したモード、またはリポジトリ固有方針が不正な場合は、制御機構の評価失敗として `BLOCKED` にする。

リポジトリ固有方針が存在しないことは正常であり、信頼済み最低基準をそのまま使用する。

## 適合保証

回帰検査では次を確認する。

- 信頼済み起動処理が対話用途として明示的に `warn` を選択できる
- リポジトリ側が信頼済み起動処理の指定したモードを弱められない
- 起動処理からの弱化指定がない場合、リポジトリ側の `warn` が信頼済みの `restricted` を弱められない
- リポジトリ側の `false` が信頼済み必須要件を解除できない
- リポジトリ側がモードや必須要件を強化できる
- リポジトリ側がキャッシュ時間を短縮できるが延長できない
- リポジトリ宣言の識別情報が追加の整合性検査として機能する
- 不正な起動処理モードや方針は安全側へ失敗する

## 再評価条件

方針語彙に、真偽値ではない要件、順序付き制約、例外、範囲付き権限などが追加され、`OR` / `max` / `min` では単調合成を正しく表現できなくなった場合に再評価する。
