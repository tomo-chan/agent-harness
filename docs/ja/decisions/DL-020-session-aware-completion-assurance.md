# DL-020 — 現在の権威的なリポジトリ状態から読み取り専用の完了を判定する

- 日付: 2026-09-06
- 状態: 採用。信頼できる作業状態情報が利用可能になった場合に再評価
- 対象: セッション開始 / 停止 / 決定的な完了保証

## 判断

完了保証では、書込み可能なローカル状態領域へ権威を持つセッション開始時基準を保存せず、ローカルの遠隔追跡参照も遠隔側の権威的な根拠として扱わない。

停止時にリポジトリ保護状態と現在のGit状態を再評価し、確認済みGitHubリポジトリから既定ブランチの現在の先頭コミットを直接取得する。次の条件をすべて確認できた場合だけ、成果物向け完了検査を省略する。

- 権威的なリポジトリ保護状態検査によって、確認済みリポジトリと既定ブランチを特定できる
- 現在のブランチが、その確認済み既定ブランチである
- 未追跡ファイルを含め、作業ツリーがクリーンである
- ローカルの `HEAD` が、GitHubから直接取得した既定ブランチの先頭コミットSHAと完全に一致する

それ以外の状態では、確認不能な場合も含め、通常の決定的な成果物向け完了検査を実行する。

セッション開始時には完了保証に関する説明文を追加してもよいが、権威を持つ完了基準は保存しない。

## 理由

従来の停止時検査は、すべてのセッションに機能ブランチと上流ブランチを要求していたため、既定ブランチ上で行うレビューや調査だけの読み取り専用セッションまで失敗していた。

最初の具体化では、セッション開始時と停止時のGit状態を比較した。しかしモデルレビューにより、その基準状態が、リポジトリコードと同じOS利用者権限で書き換え可能なローカル状態領域に保存されていることが分かった。評価対象自身が書き換えられる根拠を、独立した保証根拠として使用することはできない。

次の具体化では、その基準状態を廃止したものの、ローカル `HEAD` を `origin/<既定ブランチ>` と比較していた。ところが遠隔追跡参照も同一利用者権限で書き換え可能であり、独立した遠隔権威を表す根拠にはならない。

修正後の具体化では、停止時に二つの権威領域から新たに根拠を確立し、より限定された問いを評価する。

> 現在のリポジトリは確認済み既定ブランチ上でクリーンであり、ローカル `HEAD` は確認済みGitHubリポジトリが直接返す既定ブランチの先頭コミットと一致しているか。

この条件を満たす場合、ローカルに未完了のリポジトリ成果物は存在しないため、成果物向け完了検査を省略できる。それ以外の場合は通常の完了検査を実行する。

## 具体化・保証・進化モデル上の位置づけ

この判断は、モデルレビューによる反復的な具体化を示している。各段階で主張を狭め、その主張を支える根拠の権威を強めてきた。

```text
書換え可能なセッション開始時基準         -> 権威として使用しない
ローカルの origin/<既定ブランチ>         -> 遠隔権威として使用しない
新たに評価した保護状態                   -> リポジトリ識別・既定ブランチの根拠
GitHubから直接取得した既定ブランチSHA     -> 権威的な遠隔根拠
現在のローカルHEAD・作業ツリー            -> ローカルリポジトリの根拠
それ以外 / 不明                           -> 通常の成果物向け完了検査
```

この主張はリポジトリ成果物の状態に限定する。セッション中に外部システムへの副作用がなかったことまでは保証しない。

## 失敗時の扱い

リポジトリ保護状態、確認済みリポジトリ、既定ブランチ、現在ブランチ、作業ツリーの清浄性、ローカル `HEAD`、GitHub側の既定ブランチ先頭SHAのいずれかを確立できない場合、読み取り専用の例外を適用しない。通常の完了検査を実行する。

## 適合保証

回帰検査では次を確認する。

- セッション開始時に権威的な完了基準を保存しない
- 確認済み既定ブランチがクリーンで、ローカル `HEAD` がGitHubから直接取得した既定ブランチSHAと一致する場合だけ成果物向け完了検査を省略する
- 機能ブランチでは成果物向け完了検査を実行する
- 既定ブランチが汚れている場合は成果物向け完了検査を実行する
- ローカル `HEAD` がGitHub側と乖離している場合は成果物向け完了検査を実行する
- ローカルの `origin/<既定ブランチ>` を偽造しても権威的根拠として参照しない
- GitHub側の既定ブランチSHAを取得できない場合は読み取り専用の例外を適用しない
- 保護状態が確認不能または `BLOCKED` の場合は読み取り専用の例外を適用しない

## 再評価条件

ベンダーまたは信頼済み起動処理が、レビュー作業と成果物変更作業を直接区別できる信頼済みの作業種別、変更結果、取引状態などを提供し、リポジトリコードが変更可能な根拠へ依存せずに判定できるようになった場合に再評価する。
