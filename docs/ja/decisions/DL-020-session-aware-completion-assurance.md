# DL-020 — リポジトリ状態が変化した場合だけ成果物完了保証を適用する

- 日付: 2026-09-06
- 状態: 採用。信頼できる作業種別情報が利用可能になった場合に再評価
- 対象: セッション開始 / 停止 / 決定的な完了保証

## 判断

セッション開始時に、次のGit状態を決定的な基準として保存する。

- リポジトリのルート
- `HEAD`
- 未追跡ファイルを含む、正確な作業ツリー状態

停止時に、現在の状態とセッション開始時の状態を比較する。

- 両者が同一なら、読み取り専用セッションとして扱い、成果物向け完了検査を省略する。
- リポジトリ状態が変化していれば、通常の決定的な完了検査を実行する。
- 基準状態が欠落、不正、または信頼できる比較ができない場合は読み取り専用と推定せず、通常の完了検査を実行する。

## 理由

従来の停止時検査はすべてのセッションに対して機能ブランチと上流ブランチを要求していた。そのため、既定ブランチ上で行うレビューや調査だけの読み取り専用セッションまで失敗していた。

ツール呼出し履歴だけでは、実際にリポジトリ状態が変わったかを確実に判断できない。許可した変更操作が失敗する場合もあれば、別プロセスが間接的に変更する場合もあり、ベンダーによってツール意味論も異なる。したがって、セッション前後の実際のGit状態を比較する方が、保証したい問いに直接対応する。

## 具体化・保証・進化モデル上の位置づけ

抽象的な完了保証の主張は、成果物を変更する作業に対して適用されるものであり、あらゆるエージェントセッションに一律適用されるものではない。従来の具体化では「セッション終了」と「成果物状態の変更」を同一視していた。

進化後の具体化では、成果物状態が変化したかどうかを決定的な根拠として記録し、その根拠に応じて完了保証を選択する。

```text
リポジトリ状態が不変 -> 読み取り専用として完了
状態が変化または不明 -> 成果物向け完了検査を実行
```

## 失敗時の扱い

セッション開始時の基準状態を取得・読込みできない場合でも、完了検査を迂回しない。比較不能という未知状態では、より厳しい通常の完了検査を選択する。

## 適合保証

回帰検査では次を確認する。

- `HEAD` と作業ツリーが不変なら成果物向け完了検査を省略する
- `HEAD` が変化した場合は通常の完了検査を実行する
- 作業ツリーが変化した場合は通常の完了検査を実行する
- 基準状態が欠落または不正な場合は読み取り専用とみなさない

## 再評価条件

ベンダーが、レビュー作業と成果物変更作業をGit状態比較より直接的に区別できる、信頼済みの作業種別・変更結果・取引状態を提供するようになった場合に再評価する。
