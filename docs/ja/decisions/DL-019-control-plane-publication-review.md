# DL-019 — 制御機構の変更は公開時に審査する

- 日付: 2026-09-06
- 状態: 採用。構造化された変更操作が利用可能になった場合に再評価
- 対象: ハーネス制御機構 / SCM公開 / 承認

## 判断

制御機構に対する変更は、編集方法ではなく、既定ブランチとの差分を根拠として公開境界で明示承認を要求する。

現在の保護対象は次のとおり。

- `.agent-harness/`
- `.claude/`
- `.codex/`
- `.devin/`
- `.github/workflows/`
- `reference/harness/`
- `reference/hooks/`
- `reference/posture/`
- `reference/policies/`
- `reference/launcher/`
- `AGENTS.md`

正規形の `git push` または自律的な `gh pr create` の前に、`origin/<既定ブランチ>...HEAD` に対する変更ファイル一覧を評価する。保護対象が含まれる場合、意味論検証は規則 `control-plane-publication` の承認要求を返す。

信頼済みの外部承認によって、この最終的な承認要求を許可できる。ただしリポジトリ権威状態を先に評価するため、`BLOCKED` や `RESTRICTED` を承認によって弱めることはできない。

## 理由

編集時のパス検査は有用だが完全ではない。保護対象ファイルは、書込み・編集ツール、`apply_patch`、`git checkout` / `git restore`、リポジトリ内スクリプト、許可済みコード実行など複数の方法で変更できる。

すべての変更手段をパス認識型にしようとすると、ベンダー固有で大きな仲介面が必要になる。公開時の差分検査では、より直接的に次の問いを評価できる。

> 公開しようとしているブランチに、制御機構への変更が含まれているか。

これは変更がどの経路で作られたかに依存しない。

## 具体化・保証・進化モデル上の位置づけ

モデルレビューにより、「制御機構の変更には承認が必要」という抽象的主張を、編集時のツール分類だけへ具体化していたことが不十分だと分かった。変更対象パスを提示しない変更経路が存在するためである。

進化後の具体化では、この主張を公開時の根拠、すなわちGit差分へ対応付ける。決定的な適合保証規則は、その差分に保護対象パスが含まれるかをSCM公開前に検査する。

この規則の最初の実装では、パス正規化に `lstrip("./")` を使ったため、`.github/...` の先頭の `.` まで削除され、保護対象として認識できない欠陥があった。回帰検査がこの不一致をマージ前に検出したため、先頭の文字集合を削除するのではなく、実際の `./` 接頭辞だけを取り除く実装へ修正した。

これは具体化・保証・進化モデルの進化過程そのものである。モデルレビューによって新しい主張を得て、決定的な適合保証が具体実装の欠陥を発見し、その修正結果を回帰検査として固定した。

## 失敗時の扱い

リモート既定ブランチを特定できない場合、または公開差分を確立できない場合は、安全側へ倒して拒否する。

## 対象外

この仕組みは、ローカルの制御機構ファイルを変更不能にすることを目的としない。本番での権威は引き続き読み取り専用の信頼済みハーネス領域が担う。この判断は、リポジトリ上の制御機構変更を公開・審査する境界を定めるものである。

## 再評価条件

すべてのファイル変更操作について構造化された変更対象をベンダーが提供するようになった場合、またはSCM公開が構造化された専用操作となり、審査済み差分根拠を直接渡せるようになった場合に再評価する。
