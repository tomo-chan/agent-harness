# DL-019 — 制御機構の変更は公開時に審査する

- 日付: 2026-09-06
- 状態: 採用。構造化された変更操作が利用可能になった場合に再評価
- 対象: ハーネス制御機構 / SCM公開 / 承認

## 判断

制御機構に対する変更は、編集方法ではなく公開差分を根拠として公開境界で明示承認を要求する。その差分の基準には、ローカルで書き換え可能な遠隔追跡参照ではなく、確認済みGitHubリポジトリから直接取得した既定ブランチ先頭SHAを使用する。

現在の保護対象は次のとおり。

- `.agent-harness/`
- `.claude/`
- `.codex/`
- `.devin/`
- `.github/workflows/`
- `.github/pull_request_template.md`
- `reference/claude/`
- `reference/codex/`
- `reference/harness/`
- `reference/hooks/`
- `reference/posture/`
- `reference/policies/`
- `reference/launcher/`
- `reference/scripts/`
- `reference/kubernetes/`
- `AGENTS.md`

正規形の `git push` または自律的な `gh pr create` の前に、次の順序で評価する。

1. 新たに評価したリポジトリ保護状態から、確認済みリポジトリと既定ブランチを取得する。
2. そのGitHubリポジトリから既定ブランチの現在の先頭SHAを直接取得する。
3. そのコミットオブジェクトがローカルに存在することを確認する。
4. `git diff --name-only <GitHub既定ブランチ先頭SHA>...HEAD` で変更ファイルを取得する。
5. 保護対象が含まれる場合、規則 `control-plane-publication` の承認要求を返す。

信頼済みの外部承認によって、この最終的な承認要求を許可できる。ただしリポジトリ権威状態を先に評価するため、`BLOCKED` や `RESTRICTED` を承認によって弱めることはできない。

## 理由

編集時のパス検査は有用だが完全ではない。保護対象ファイルは、書込み・編集ツール、`apply_patch`、`git checkout` / `git restore`、リポジトリ内スクリプト、許可済みコード実行など複数の方法で変更できる。

すべての変更手段をパス認識型にしようとすると、ベンダー固有で大きな仲介面が必要になる。公開時の差分検査では、より直接的に次の問いを評価できる。

> 権威的な現在の既定ブランチを基準にしたとき、公開しようとしているブランチに制御機構への変更が含まれているか。

これは変更がどの経路で作られたかに依存しない。

また、差分の基準SHA自体も保証根拠の一部である。ローカルの `origin/<既定ブランチ>` は、リポジトリコードと同じOS利用者権限から `refs/remotes/origin/*` を書き換えられるため、独立した遠隔根拠にはできない。そのため基準SHAはGitHubから直接取得し、ローカル遠隔追跡参照はこの権威判断に使用しない。

## 具体化・保証・進化モデル上の位置づけ

最初のモデルレビューでは、「制御機構の変更には承認が必要」という抽象的主張を、編集時のツール分類だけへ具体化していたことが不十分だと分かった。変更対象パスを提示しない変更経路が存在するためである。そこで主張を公開時のGit差分へ対応付けた。

その後のモデルレビューでは、差分の基準に使っていた `origin/<既定ブランチ>` 自体が評価対象から変更可能であることを発見した。したがって具体化をさらに進化させた。

```text
編集手段が示す変更パス                 -> 根拠の網羅性が不足
ローカル origin/<既定ブランチ>         -> 可変であり遠隔権威ではない
GitHubの既定ブランチ先頭SHA             -> 権威的な遠隔基準
そのSHAからHEADまでのGit差分             -> ローカル変更パスの根拠
```

この規則の最初の実装では、パス正規化に `lstrip("./")` を使ったため、`.github/...` の先頭の `.` まで削除される欠陥もあった。回帰検査がこの不一致をマージ前に検出し、実際の `./` 接頭辞だけを取り除く実装へ修正した。

これらは具体化・保証・進化モデルの進化過程そのものである。モデルレビューが主張と根拠モデルを改善し、決定的な適合保証がその具体化からの逸脱を検出する。

## 失敗時の扱い

確認済みリポジトリまたは既定ブランチを特定できない場合、GitHubから現在の既定ブランチ先頭SHAを取得できない場合、そのコミットオブジェクトがローカルに存在しない場合、または公開差分を確立できない場合は、安全側へ倒して拒否する。ローカル遠隔追跡参照へは代替しない。

## 対象外

この仕組みは、ローカルの制御機構ファイルを変更不能にすることを目的としない。本番での権威は引き続き読み取り専用の信頼済みハーネス領域が担う。この判断は、リポジトリ上の制御機構変更を公開・審査する境界を定めるものである。

## 再評価条件

すべてのファイル変更操作について構造化された変更対象をベンダーが提供するようになった場合、またはSCM公開が構造化された専用操作となり、審査済み差分根拠を直接渡せるようになった場合に再評価する。
