# S1 — 信頼済み実行境界と方針基盤

## 状態

実装移植と初回レビューを完了。初期のファイル割当をそのまま採用せず、保証責務に基づいて境界を具体化した。

## 主張

1. 保証機構として利用するハーネス実装と方針は、評価対象リポジトリから変更できない信頼済み領域に置かれる。
2. 方針評価は `deny > ask > allow` を明示的な優先順位とし、方針読込み・検証・評価不能時は許可へ倒れない。
3. 実行時に利用する方針は信頼済み起動処理が指定し、評価対象リポジトリ内の既定パスへ暗黙にフォールバックしない。

> リポジトリ保護状態に関する「信頼済み最低基準とリポジトリ固有設定の単調合成」はS2の責務とする。初期S1主張に含めていた「リポジトリ固有方針は信頼済み最低基準を弱化できない」は、具体化の結果、S2へ境界を移した。

## 権威と責任境界

- 権威: 読み取り専用として配備される信頼済みハーネス領域、信頼済み起動処理、配備基盤。
- 観測: 実行時環境、正規化されたツール入力、方針入力。
- 外部責任:
  - 配備基盤が信頼済みハーネス領域を評価対象リポジトリから書込み不能にすること。
  - 実際のフック接続が `trusted_policy_hook.py` を権威ある入口として使用し、評価対象リポジトリが直接アダプタへ迂回できないこと。
- 後続スライスへ委譲:
  - リポジトリ同一性・GitHub保護状態・最低基準の単調合成: S2
  - SCM公開意味論: S3
  - 制御機構変更の公開審査: S4
  - 完了判定: S5
  - Claude Code / Codex / Devin 固有の接続と配備具体化: S6

## 保証契約

- `AGENT_HARNESS_TRUSTED_ROOT` が未指定、または実際のハーネス配置と一致しない場合は実行を拒否する。
- 信頼済み方針の指定が信頼済みルート外へ解決される場合は拒否する。
- S1では汎用方針アダプタを固定し、環境変数によるアダプタ差替えを許可しない。ベンダー固有接続はS6で具体化する。
- 方針アダプタは `AGENT_HARNESS_POLICY` を必須の信頼済み入力として扱い、従来の `AGENT_POLICY` やリポジトリ内の方針ファイルへフォールバックしない。
- 方針の構造、既定判断、正規表現を実行前に検証する。
- 方針評価の優先順位は JSON 内の記述順ではなく `deny > ask > allow` で固定する。
- 方針読込み・検証・入力解釈・評価に失敗した場合、境界では `deny` を返す。

## 具体化

### 実装

- `reference/launcher/trusted_policy_hook.py`
  - S1専用の信頼済み起動境界。
  - 信頼済みルートと信頼済み方針の包含関係を検証する。
  - 汎用方針アダプタを固定し、ベンダー選択は行わない。
  - `AGENT_HARNESS_POLICY` を設定し、旧 `AGENT_POLICY` を除去する。
- `reference/hooks/policy_engine.py`
  - 方針スキーマ検証。
  - `deny > ask > allow` の決定的評価。
  - CLI境界での fail-closed。
- `reference/hooks/pre_tool_use_adapter.py`
  - `AGENT_HARNESS_POLICY` のみを方針権威として使用。
  - 方針未指定・読込み失敗・評価失敗を `deny` へ変換。

### 決定的な根拠

- `reference/hooks/tests/test_policy_engine.py`
  - deny優先順位。
  - 不正な方針の拒否。
  - 信頼済み方針未指定時の deny。
  - 基本方針の回帰確認。
- `reference/launcher/tests/test_trusted_policy_hook.py`
  - 信頼済みルート必須。
  - ルート不一致の拒否。
  - 信頼済みルート外の方針指定の拒否。
  - S1アダプタが固定されていること。
  - 旧 `AGENT_POLICY` を信頼済み入口から除去すること。

## 具体化で判明した境界修正

### `reference/launcher/preflight.py`

初期スライス案ではS1へ割り当てていたが、実装は `check_repository_posture` を呼び出してリポジトリ保護状態を評価する。その成立理由と失敗形態はS2のリポジトリ権威に依存するため、S1へ移植しない。

### `reference/launcher/trusted_hook.py`

PR #1の最終形はベンダー選択と信頼済み境界を一つの起動器に持つ。S1ではベンダー固有責務を持ち込まず、`trusted_policy_hook.py` で信頼済み方針境界だけを成立させる。S6でベンダー接続を追加する際、この境界を再利用または統合する。

### 方針環境変数の不一致

PR #1の `trusted_hook.py` は `AGENT_HARNESS_POLICY` を設定する一方、従来の汎用 `pre_tool_use_adapter.py` は `AGENT_POLICY` を参照していた。この経路では信頼済み方針の利用を保証できないため、S1で `AGENT_HARNESS_POLICY` に統一し、未指定時は fail-closed とした。

### アダプタ差替え可能性

初回移植では `AGENT_HARNESS_TRUSTED_ADAPTER` により信頼済みルート内の別アダプタを選択できた。しかしS1の主張はベンダー選択を含まず、汎用方針境界だけを保証するため、アダプタを固定した。ベンダー固有の選択・正規化はS6へ委譲する。

## 残存リスクと対象外

- 読み取り専用の信頼済み領域そのものは配備基盤が強制する。S1単独のローカルテストではこの外部保証を証明しない。
- `trusted_policy_hook.py` が権威ある実行入口として強制されることはベンダー接続・配備具体化に依存し、S6で保証する。
- 現在の例示方針に含まれる個々のSCMルールの意味論的妥当性はS3以降の保証対象であり、S1では方針評価機構そのものだけを扱う。

## 収束判定

S1内部のモデル・具体化・実装について、初回レビューで新たなマージ阻害指摘は残っていない。

ただし、S1の主張1を実運用上成立させるための読み取り専用配備と権威あるフック接続はS6の外部責任である。この依存関係を明示した状態をS1の収束条件とし、S6で配備具体化が成立しない場合はS1の保証も成立しない。
